# Project Structure

This document explains the organization of the SKR-Pico Encoder Monitor project.

## Directory Layout

```
encoder_monitor/
│
├── config.h                    # Pin definitions and global configuration
├── main.c                      # Main application code
│
├── src/                        # Library source files
│   ├── lcd_i2c.h              # I2C LCD library header
│   ├── lcd_i2c.c              # I2C LCD library implementation
│   ├── encoder.h              # Rotary encoder library header
│   └── encoder.c              # Rotary encoder library implementation
│
├── CMakeLists.txt             # CMake build configuration
├── pico_sdk_import.cmake      # Pico SDK import script (standard)
│
├── .vscode/                   # VSCode IDE configuration
│   ├── settings.json          # Editor settings
│   ├── c_cpp_properties.json  # IntelliSense configuration
│   └── launch.json            # Debug configuration
│
├── README.md                  # Comprehensive documentation
├── QUICKSTART.md              # Quick start guide
└── .gitignore                 # Git ignore rules
```

## File Descriptions

### Root Level Files

| File | Purpose |
|------|---------|
| `config.h` | All pin definitions, constants, and global configuration |
| `main.c` | Main program entry point and application logic |
| `CMakeLists.txt` | CMake build system configuration |
| `pico_sdk_import.cmake` | Standard Pico SDK import script |

### src/ Directory

Contains modular library code that can be reused in other projects.

| File | Purpose |
|------|---------|
| `lcd_i2c.h` | LCD library API declarations |
| `lcd_i2c.c` | LCD library implementation (PCF8574 I2C backpack) |
| `encoder.h` | Encoder library API declarations |
| `encoder.c` | Encoder library implementation (quadrature decoding) |

### .vscode/ Directory

VSCode IDE configuration for improved development experience.

| File | Purpose |
|------|---------|
| `settings.json` | Editor preferences and formatting rules |
| `c_cpp_properties.json` | IntelliSense include paths and compiler settings |
| `launch.json` | Debug configuration for OpenOCD/GDB |

## Build Output Structure

After building, the following directory structure is created:

```
encoder_monitor/
│
├── build/                     # Generated by CMake (git-ignored)
│   ├── encoder_monitor.elf    # ELF binary (for debugging)
│   ├── encoder_monitor.bin    # Binary file
│   ├── encoder_monitor.hex    # Hex file
│   ├── encoder_monitor.uf2    # UF2 file (for flashing)
│   ├── encoder_monitor.map    # Memory map
│   └── ...                    # Other build artifacts
```

## Include Paths

The project is configured with the following include paths:

1. **Project root** - For `config.h` and `main.c`
2. **src/** - For library headers (`lcd_i2c.h`, `encoder.h`)
3. **Pico SDK paths** - Automatically added by CMake

### How Includes Work

In `main.c`:
```c
#include "config.h"              // From project root
#include "src/lcd_i2c.h"         // From src/ directory
#include "src/encoder.h"         // From src/ directory
```

In `src/lcd_i2c.c`:
```c
#include "lcd_i2c.h"             // Same directory (src/ is in include path)
```

In `src/encoder.c`:
```c
#include "encoder.h"             // Same directory (src/ is in include path)
```

## Modifying the Structure

### Adding a New Library

1. Create `src/mylib.h` and `src/mylib.c`
2. Update `CMakeLists.txt`:
   ```cmake
   add_executable(encoder_monitor
       main.c
       src/lcd_i2c.c
       src/encoder.c
       src/mylib.c          # Add your library
   )
   ```
3. Include in `main.c`:
   ```c
   #include "src/mylib.h"
   ```

### Organizing Hardware Configurations

Create separate config files for different hardware setups:

```
encoder_monitor/
├── config.h                    # Default configuration
├── config_skr_pico.h          # SKR-Pico specific
├── config_pico.h              # Standard Pico
└── config_custom.h            # Custom board
```

Then in `main.c`:
```c
#ifdef USE_SKR_PICO
    #include "config_skr_pico.h"
#else
    #include "config.h"
#endif
```

## Why This Structure?

### Benefits

1. **Modularity** - Libraries in `src/` can be reused in other projects
2. **Clean Root** - Main files are easy to find
3. **IDE Integration** - VSCode configuration is self-contained
4. **Build Isolation** - Build artifacts go in `build/`, not mixed with source
5. **Standard Layout** - Follows common C project conventions

### Scalability

This structure scales well for larger projects:

```
encoder_monitor/
├── src/
│   ├── drivers/        # Hardware drivers
│   ├── utils/          # Utility functions
│   └── peripherals/    # Peripheral libraries
├── include/            # Public headers (if making a library)
├── tests/              # Unit tests
└── docs/               # Additional documentation
```

## Best Practices

1. **Keep `config.h` hardware-specific** - All pin definitions and hardware constants
2. **Make libraries hardware-agnostic** - `src/` libraries should not include `config.h`
3. **One feature per library** - Keep `lcd_i2c` and `encoder` separate
4. **Document public APIs** - Add comments to `.h` files
5. **Use meaningful names** - `encoder.c` not `enc.c`

## Git Workflow

The `.gitignore` excludes:
- `build/` - Generated files
- `*.uf2`, `*.elf`, etc. - Build outputs
- IDE-specific files - User preferences

Commit to version control:
- All `.c` and `.h` files
- `CMakeLists.txt`
- Documentation files
- `.vscode/` if team uses VSCode

## Summary

This project structure balances simplicity with organization, making it easy to:
- **Build** - Simple CMake workflow
- **Navigate** - Logical file organization
- **Extend** - Add new features easily
- **Reuse** - Extract libraries for other projects
- **Maintain** - Clear separation of concerns
